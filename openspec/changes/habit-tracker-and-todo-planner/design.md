## Context

当前应用是一个基于 React + Vite 的 Todo List PWA 子应用（Garfish 架构），使用 Local Storage 进行数据持久化。应用结构为单页面、单模块，所有逻辑集中在 `App.jsx` 中。

用户希望在此基础上扩展两个新模块：**习惯打卡**和**待办计划**。这两个模块与现有 Todo List 在功能定位上有明显差异——习惯打卡注重长期累积与无压力记录，待办计划注重优先级排序与时间推算。因此需要引入多页面路由和模块化架构。

约束条件：
- 继续使用 React + Vite 技术栈
- 数据持久化仍基于 Local Storage（各模块数据隔离）
- 保持 PWA 可安装与离线能力
- 保持 Garfish 子应用生命周期兼容
- 不引入后端服务

## Goals / Non-Goals

**Goals:**
- 设计清晰的多模块前端架构，支持习惯打卡、待办计划与原有 Todo List 共存
- 习惯打卡模块：支持创建习惯（名称、寄语、开始时间、颜色）、当日打卡、日历补卡、累计统计
- 待办计划模块：支持创建待办（名称、预计时长）、手动排序、自动推算截止日期、完成归档与表扬
- 设计合理的 Local Storage 数据结构，各模块独立存储
- 应用内导航流畅，界面层次清晰

**Non-Goals:**
- 不实现用户登录与多设备同步
- 不实现习惯的周/月/年统计对比功能（设计上明确排除）
- 不实现服务端数据存储
- 不实现通知/提醒功能
- 不实现待办事项的子任务拆分

## Decisions

### 决策 1：路由方案 — 使用 React Router v6 + Hash Router

**选择**: `react-router-dom` 的 `HashRouter`

**理由**: Hash 路由天然兼容 Garfish 子应用的 basename 隔离机制，无需服务端配置 fallback，且在 PWA 离线场景下表现稳定。

**替代方案**:
- `BrowserRouter`: 需要服务端配置 fallback，与 Garfish 子应用集成复杂度更高
- 手动状态路由: 灵活但缺少 URL 同步与浏览器前进后退支持

### 决策 2：页面结构设计

**选择**: 底部 Tab 导航 + 多页面结构

页面规划：
| 路由 | 页面 | 说明 |
|------|------|------|
| `/` | 习惯打卡首页 | 当日打卡界面 + 新增习惯入口 |
| `/habit/calendar` | 补卡日历 | 选择日期 → 选择习惯 → 补卡 |
| `/planner` | 待办计划 | 待办列表（可排序）+ 新增待办 |
| `/planner/done` | 已完成 | 已完成事项归档与表扬 |
| `/todo` | 原 Todo List | 保留现有功能不变 |

**理由**: 底部 Tab 导航是移动端 PWA 最直观的交互模式，用户可快速切换核心功能。

### 决策 3：数据结构设计 — 各模块独立 Storage Key

**习惯数据** (`habit-tracking/habits`):
```json
{
  "version": 1,
  "items": [
    {
      "id": "uuid",
      "name": "阅读",
      "motto": "每天进步一点点",
      "startDate": "2026-03-01",
      "color": "#4CAF50",
      "createdAt": 1711900000000
    }
  ]
}
```

**打卡记录** (`habit-tracking/checkins`):
```json
{
  "version": 1,
  "records": {
    "habitId1": ["2026-03-01", "2026-03-02", "2026-03-05"]
  }
}
```

打卡记录使用 `habitId → 日期字符串数组` 的扁平结构，查询某天是否打卡为 O(1)（Set 化），累计总量为数组长度。不记录时间，只记录日期（`YYYY-MM-DD`），满足"只需日期无需时间"的需求。

**待办计划数据** (`todo-planner/items`):
```json
{
  "version": 1,
  "items": [
    {
      "id": "uuid",
      "title": "准备面试",
      "durationDays": 5,
      "sortOrder": 0,
      "completed": false,
      "completedAt": null,
      "createdAt": 1711900000000
    }
  ]
}
```

排序字段 `sortOrder` 为整数，排序后系统自动按顺序累加 `durationDays` 计算每项的推算截止日期。

**理由**: 各模块使用独立的 Storage Key 避免数据耦合，结构简单直观，便于独立迭代。扁平的日期数组比嵌套的日历结构更适合"只关心累计量"的场景。

### 决策 4：日历组件 — 自行实现轻量日历

**选择**: 自行实现简单的月历网格组件

**理由**: 补卡日历只需展示月历并选择日期，功能需求明确且简单。自行实现可避免引入大体积第三方日历库，保持 PWA 包体积精简。

**替代方案**:
- `react-calendar`: 功能完善但包体积较大，且样式定制需额外工作
- `date-fns` + 自定义: 可作为日期计算辅助，但日历 UI 仍需自行实现

### 决策 5：待办排序 — 手动排序 + 自动推算

**选择**: 使用拖拽排序（或上下移动按钮）调整优先级，系统自动从"今天"开始按排序顺序累加 `durationDays` 推算截止日期。

**推算逻辑**:
1. 将未完成待办按 `sortOrder` 升序排列
2. 第一项的推算截止日 = 今天 + 该项的 `durationDays`
3. 第 N 项的推算截止日 = 第 N-1 项的推算截止日 + 第 N 项的 `durationDays`
4. 每次新增或重排后重新计算所有推算日期

**理由**: 简单直观，用户只需关注"哪个更重要排前面"，系统自动告知"大概几号前要完成"。每次排序变更后所有后续事项自动推迟，符合用户"所有待办根据排序自动推迟"的需求。

### 决策 6：已完成事项展示 — 独立页面 + 表扬反馈

**选择**: 已完成事项移入独立的"/planner/done"页面，完成时显示表扬动效（如 emoji 🎉 + 鼓励文字），归档页按完成时间倒序展示灰显条目。

**理由**: 独立页面让待办列表保持清爽（只看未完成的），同时保留所有历史记录供回顾。表扬反馈增加正向激励。

## Risks / Trade-offs

- **[Local Storage 容量限制]** → 习惯打卡记录随时间增长可能接近 5MB 上限。**缓解**: 日期字符串数组非常紧凑，即使 10 个习惯每天打卡持续 10 年也仅约 1MB。短期内无风险，长期可考虑压缩或迁移 IndexedDB。
- **[无数据同步]** → 用户更换设备或清除浏览器数据会丢失记录。**缓解**: 明确告知用户数据仅存本地，后续可考虑导出/导入功能。
- **[日历自行实现维护成本]** → 自定义日历组件需处理月份切换、闰年等边界情况。**缓解**: 功能范围有限（仅选择日期），复杂度可控；可借助 `Date` 原生 API 处理日期计算。
- **[拖拽排序在移动端体验]** → 移动端拖拽交互不够直观。**缓解**: 同时提供上下移动按钮作为备选操作方式。
- **[路由引入增加包体积]** → `react-router-dom` 约 12KB gzipped。**缓解**: 相对于功能收益可接受，且为行业标准方案。
