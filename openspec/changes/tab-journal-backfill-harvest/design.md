## Context

当前应用是一个基于 React + Vite 的习惯打卡 PWA，白色基底 + 多巴胺色系。底部仅有一个"习惯打卡"Tab，补卡页面是首页的子路由。打卡数据模型为 `{ [habitId]: string[] }` — 每个习惯存储日期字符串数组，同日期去重。

本次变更需要：(1) 底部导航扩展为三个 Tab；(2) 打卡模型升级为时间戳数组以支持同天多打；(3) 补卡日历增强（多色渐变标记、删卡）；(4) 新增收获集统计页面和渔获模块。

## Goals / Non-Goals

**Goals:**
- 底部导航扩展为「今日记」「时光补」「收获集」三个 Tab
- 打卡记录从日期字符串改为 ISO 时间戳，支持同一天多次打卡
- 补卡日历支持多色渐变标记、习惯选择器下移放大、删卡
- 收获集页面展示统计图表 + 渔获随机数据模块
- 保持 PWA、Garfish 子应用兼容性不变

**Non-Goals:**
- 不实现服务端同步（仍用 Local Storage）
- 不做图表的无障碍（ARIA）优化
- 不做打卡记录的导入/导出
- 渔获模块本期不做真实异步拉取，仅预留接口结构

## Decisions

### 决策 1：打卡数据结构升级 — 时间戳数组

**选择**: 将 `records[habitId]` 从 `string[]`（日期字符串）改为 `number[]`（Unix 毫秒时间戳）

新结构：
```json
{
  "version": 2,
  "records": {
    "habit-id-1": [1711872000000, 1711875600000, 1711958400000]
  }
}
```

**迁移策略**: loadCheckins 检测 version=1 时自动迁移 — 将每个日期字符串转为当天 12:00:00 的时间戳，然后写回 version=2。迁移一次性完成，静默执行。

**理由**: 时间戳可以天然支持同天多次打卡（不同时间戳），同时通过 `new Date(ts).toISOString().slice(0, 10)` 可轻松提取日期字符串以兼容日历等按天显示的场景。数组推入新时间戳即可，无需去重逻辑。

**替代方案**:
- 保持日期字符串 + 额外计数字段：结构复杂，查询不直观
- 使用 `{ date: string, count: number }[]`：丢失每次打卡的精确时间，不利于未来细粒度分析

### 决策 2：图表实现 — 纯 SVG/Canvas 自绘

**选择**: 不引入第三方图表库，使用纯 SVG 元素 + CSS 动画手动实现 3 类图表：
1. **热力图**（全年日历格子）：类 GitHub contribution grid，按天统计打卡次数映射颜色深浅
2. **趋势折线图**：最近 30 天打卡次数走势，SVG `<polyline>`
3. **习惯占比环形图**：各习惯打卡次数占比，SVG `<circle>` stroke-dasharray

**理由**: 三类图表结构简单，自绘代码量可控（各 50-100 行），避免引入 chart.js（~200KB）或 recharts（~150KB）等重依赖。与多巴胺色系的样式融合更灵活。

**替代方案**:
- chart.js / recharts：功能强大但包体积大，对于 3 个简单图表性价比低
- echarts：更重，不适合轻量 PWA

### 决策 3：日历多色渐变标记

**选择**: 当某天有多个习惯的打卡记录时，该日期格子背景使用 CSS `linear-gradient` 拼接各习惯颜色。每种习惯在该天只要出现过一次就算出现（按天去重后取习惯颜色集合）。

实现：在 Calendar 组件中 `markedDates` 从 `{ [date]: string }` 改为 `{ [date]: string[] }` — 值为颜色数组。单色时直接用 `background: color`，多色时用 `background: linear-gradient(135deg, color1 50%, color2 50%)` 或更多色段。

**理由**: 纯 CSS 实现，无需额外依赖，视觉效果直观，用户一眼就能看出某天打了哪些习惯。

### 决策 4：渔获模块交互

**选择**: 底部固定按钮「🎣 渔获」，点击后从底部滑入一个卡片，展示随机的一条打卡概览数据（如"你在阅读上已经坚持了 42 次！"或"上周你打卡最多的习惯是冥想"）。卡片 3 秒后自动收起，也可手动关闭。

数据源为本地打卡记录的聚合统计，随机选取一条展示。预留 `fetchInsight(): Promise<InsightData>` 接口，当前实现为同步返回本地数据包装的 Promise，未来可替换为网络请求。

**理由**: 随机展示增加趣味性和惊喜感，底部滑入动画不打断用户当前操作。Promise 接口设计便于未来无缝切换到异步数据源。

### 决策 5：补卡页面习惯选择器布局

**选择**: 习惯选择器从日历上方移到下方，每个习惯按钮使用习惯自选颜色作为背景色（浅色调），按钮更大（padding 增大，font-size 增大），类似"标签墙"的感觉。选中态为颜色加深 + 边框高亮。

**理由**: 下方放置符合「先看日历选日期 → 再选习惯」的操作顺序。大尺寸按钮在移动端更易点击，彩色背景让选择器视觉上更丰富活泼。

### 决策 6：删卡交互流程

**选择**: 在补卡页面选中日期后，下方展示该日期的已有打卡记录列表（显示习惯名和打卡时间）。每条记录旁有一个「×」删除按钮，点击后弹出确认，确认后删除该条时间戳记录。

**理由**: 细粒度展示每条记录，用户可以精确删除某一次打卡而非清除整天所有记录。与补卡操作在同一界面，形成"增/删"闭环。

## Risks / Trade-offs

- **[数据迁移风险]** → version 1 → 2 的自动迁移会改变原有数据格式。**缓解**: 迁移前在 console.log 记录原始数据快照，迁移逻辑简单（日期转时间戳）且可逆。
- **[自绘图表维护成本]** → 纯 SVG 图表无法像图表库那样快速增加新类型。**缓解**: 当前只需 3 类固定图表，复杂度可控；若未来需要更多图表再评估引入库。
- **[热力图数据量]** → 全年 365 天 × 多个习惯的数据遍历可能在数据量大时变慢。**缓解**: 热力图按年计算，数据在页面加载时一次性计算并缓存，后续切换年份才重算。
- **[渔获模块数据单调]** → 本地数据源有限，随机展示可能重复。**缓解**: 设计 5-8 种模板句式，配合变量填充（习惯名、次数、天数、最近日期等）增加多样性。预留 Promise 接口便于未来接入更丰富的数据源。
- **[日历多色渐变]** → 超过 3-4 种颜色时渐变会显得混乱。**缓解**: 最多展示前 4 种颜色的渐变，超出部分用最后一段显示"+N"的视觉提示。
